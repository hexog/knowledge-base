## 1. Решение о переходе

По решению владельца в текущей сессии принимаем существующее состояние хранения, шлюза, MCP-интеграции и синтетического пилота как основу эксплуатации. Дополнительный контрольный прогон синтетического пилота не является условием следующей разработки.

Ограничения отчёта остаются известными: оценка 6/10 не имеет однозначной построчной методики; задержка не измерена воспроизводимо; корпус небольшой и синтетический. Эти ограничения не превращаются в новые блокирующие этапы. Дальнейшие изменения приоритизируются по наблюдаемым проблемам и обратной связи при реальной работе. Конкретные нарушения доступа, потери данных и ошибки восстановления исправляются при обнаружении.

Ранее подготовленный отчёт сохраняется как исторический документ. В новой записи решения или разделе текущего плана зафиксировать принятие состояния; прежние измерения и результаты не переписывать задним числом.

## 2. Цель

Превратить доступ к знаниям в ежедневные полезные действия:

1. Подготовить пользователя к встрече по доступным материалам.
2. Разобрать предлагаемое решение: факты, допущения, варианты, риски и недостающие сведения.
3. Зафиксировать короткую обратную связь о полезности и ошибках результата, чтобы улучшать систему точечно.

Первый инкремент использует существующий HTTP/MCP-контур и агентскую модель. Сервер базы не получает собственную генерацию ответов. Новые интеграции, векторный индекс, сложный UI и автоматическое принятие знаний не требуются для начала работы.

## 3. Реализация первого инкремента

Создать два обычных Markdown-шаблона, пригодных для использования в OpenCode и других клиентах:

- `docs/workflows/prepare-meeting.md`;
- `docs/workflows/assess-decision.md`.

Шаблоны содержат назначение, краткую форму входных данных, порядок поиска, правила проверки и структуру результата. Первое использование возможно копированием шаблона в диалог. Нативные команды конкретного клиента можно добавить отдельно, если они заметно сократят повседневные действия; содержательные инструкции должны остаться в переносимых файлах.

Добавить локальные команды владельца `kb feedback add/list/show/set-status`. Для начала этого достаточно: владелец оценивает результат после работы с агентом. Внешним MCP-клиентам не выдавать доступ к журналу обратной связи. Отдельный инструмент отправки feedback через API можно добавить, если ручная фиксация станет препятствием; это не условие первого инкремента.

## 4. Подготовка к встрече

### 4.1. Вход

Пользователь задаёт тему или проект, цель встречи и, при наличии, дату, участников и интересующий период. Достаточно темы и цели, чтобы начать работу; отсутствие остальных полей не должно превращаться в длинную анкету.

Пример:

> Подготовь меня к обсуждению обработки очередей. Цель — решить, выносить ли обработку в отдельный сервис. Интересуют принятые решения, ограничения, незакрытые вопросы и риски.

Участники и период помогают сформулировать поиск, но не считаются достоверными метаданными базы автоматически.

### 4.2. Порядок работы агента

1. Найти записи по теме через `search`, при необходимости сделать несколько запросов с альтернативными формулировками.
2. Открыть ключевые результаты через `get_record`; не строить фактические выводы только по сниппету.
3. Проверить цитаты источников и прочитать соседний контекст через `get_source_text`, если вопрос касается причин, условий или исключений.
4. Сформировать краткий бриф с проверяемыми ссылками. Неизвестное обозначить как неизвестное по доступным материалам.
5. В конце предложить пользователю отметить конкретную ошибку или недостающий важный пункт; не требовать заполнения формы для получения брифа.

Если цитата занимает строку 3, а пользователь спрашивает «почему», начать с небольшого диапазона вокруг цитаты, например строки 1–6, в пределах серверных ограничений. Нельзя делать вывод «обоснование отсутствует», прочитав только строку с решением. Если после доступного поиска причина не найдена, формулировать: «В просмотренных доступных материалах не нашёл обоснования».

Количество вызовов определяется задачей. После нескольких безрезультатных запросов агент сообщает, что именно удалось проверить, и предлагает конкретное недостающее сведение. Бесконечно расширять поиск или просить local-профиль для обхода external-отказа нельзя.

### 4.3. Результат

Краткий бриф по умолчанию содержит:

- цель встречи и 3–5 важных пунктов;
- подтверждённые решения и ограничения с источниками;
- открытые вопросы и действия, явно зафиксированные в материалах;
- оценки и риски агента, обозначенные как анализ;
- вопросы, которые полезно обсудить;
- источники и границы покрытия.

Каждое существенное фактическое утверждение содержит ID записи и ссылку на source ID/диапазон строк; для ключевых решений — короткую точную цитату. Названия разделов допустимо адаптировать под запрос, но факты и анализ должны оставаться различимыми.

Если в источнике нет владельца задачи, срока или статуса выполнения, агент не придумывает их. Предложенные агентом вопросы и действия помечаются как предложения. Не выводить изменение «с прошлой встречи», если нет материалов, позволяющих сравнить состояния.

## 5. Разбор решения

### 5.1. Вход

Пользователь описывает предложение, цель и известные ограничения. Если есть варианты и критерии выбора, они включаются в запрос. Разбор возможен и с неполным описанием — недостающие условия попадут в список допущений.

Пример:

> Оцени перенос обработки очереди в отдельный сервис. Цель — независимое масштабирование. Ограничение — без увеличения команды сопровождения. Какие факты в базе поддерживают решение, какие риски и альтернативы стоит проверить?

### 5.2. Порядок работы

Агент ищет связанные решения, ограничения, причины прежних выборов, наблюдавшиеся проблемы и доступные альтернативы. Проверяет контекст источников тем же способом, что при подготовке встречи.

Результат разделяет:

| Часть | Что включать |
| --- | --- |
| Факты | Утверждения из доступных материалов с цитатами |
| Допущения | Условия, без которых оценка не работает; источник допущения — пользователь или агент |
| Выгоды | Ожидаемые эффекты, с указанием, подтверждены ли они данными или являются гипотезой |
| Риски | Условие возникновения, возможное последствие, основание и способ уменьшения неопределённости |
| Альтернативы | Отдельно варианты из источников и новые предложения агента |
| Неизвестные сведения | Что нужно выяснить до окончательного решения |
| Рекомендация | Условный вывод и следующий практический шаг |

Для риска полезна простая таблица «риск → основание → последствие → что проверить/сделать». Не присваивать численные вероятности и оценки ущерба без исходных данных. При качественной оценке явно обозначать, что это суждение агента.

Разбор не фиксирует решение за пользователя. Новые выводы могут быть предложены для сохранения только как draft, если пользователь попросил это сделать и draft-инструмент включён. По умолчанию результат остаётся в диалоге или отдельном рабочем документе.

## 6. Совместимость с текущими возможностями

В текущем MCP доступны поиск знаний, чтение записи, чтение диапазона источника и создание draft. Шаблоны не должны обещать возможности, отсутствующие в API.

В частности:

- project/участники/период пока используются для формулировки запроса; серверной точной фильтрации по ним шаблон не имитирует;
- дата импорта не подменяет дату решения или срок действия факта;
- отсутствие результата не доказывает отсутствие сведений во всей базе: часть данных может быть закрыта или не найдена текущим поиском;
- полный граф конфликтов и версий не доступен через каждый результат MCP; обнаруженные в тексте противоречия показываются с обеими цитатами;
- нельзя читать оригиналы напрямую в обход шлюза для улучшения ответа внешней модели.

По мере реального использования можно расширять API фильтрами и контекстом записи. Конкретное расширение должно опираться на сохранённый пример неудовлетворительного результата.

## 7. Журнал обратной связи

### 7.1. Назначение

Сохранять короткое описание полезного результата или проблемы вместе с минимальным контекстом для последующего исправления. Оценка пользователя является сообщением о результате, а не автоматической правкой знания.

Журнал не должен требовать полный транскрипт разговора. По умолчанию достаточно сценария, оценки, описания проблемы и известных ссылок. Сохранять положительные примеры тоже полезно: они показывают, какие сценарии нужно сохранить при изменениях.

### 7.2. Хранение

Добавить каталог `feedback/<feedback_id>.json` в переносимую папку базы. ID — UUID, файлы UTF-8. Они не включаются в поисковую выдачу знаний и недоступны через текущий агентский API. Обратная связь может содержать сведения о закрытых материалах, поэтому для неё действует локальный доступ владельца.

Если владелец позднее захочет передать агенту отдельный пример для исправления, он явно выбирает разрешённую копию. Журнал целиком внешней модели автоматически не отправляется.

Минимальная схема:

```json
{
  "schema_version": 1,
  "id": "b6d4ff0b-7959-4252-88a4-c75caf40b550",
  "created_at": "2026-10-30T09:00:00Z",
  "updated_at": "2026-10-30T09:00:00Z",
  "workflow": "prepare_meeting",
  "rating": "partly_useful",
  "category": "incomplete_answer",
  "status": "new",
  "note": "Не учтена причина решения в соседней строке источника.",
  "expected": "Прочитать контекст цитаты и включить обоснование.",
  "record_refs": [],
  "source_refs": [],
  "gateway_request_ids": [],
  "client": "OpenCode",
  "model": null,
  "resolution": null,
  "history": [{"status": "new", "at": "2026-10-30T09:00:00Z", "reason": null}]
}
```

Допустимые workflow: `prepare_meeting`, `assess_decision`, `question`, `other`. Rating: `useful`, `partly_useful`, `not_useful`. Category: `positive`, `wrong_fact`, `incomplete_answer`, `wrong_citation`, `stale_knowledge`, `retrieval_miss`, `access_issue`, `technical`, `other`.

Refs — опциональные ссылки на известные record/source ID и, если сохранены, хэши версий. Request ID служит корреляции с аудитом, а не гарантией воспроизводимости ответа. Если причина ещё не ясна, category не должна выдавать предположение за установленный диагноз: выбрать `other` или записать гипотезу в note.

### 7.3. Команды владельца

Предлагаемый CLI:

```text
kb feedback add --workflow prepare_meeting --rating partly_useful --category incomplete_answer --note-file /path/to/note.txt
kb feedback list --status new
kb feedback show <feedback_id>
kb feedback set-status <feedback_id> --status triaged --reason "Нужно читать контекст цитаты"
```

Опциональные `--record`, `--source`, `--request-id`, `--expected-file`, `--client`, `--model` позволяют связать пример с результатом. Длинные тексты передаются файлами, чтобы не зависеть от экранирования shell. Путь note-file — явно выбранный вход владельца, а не имя файла хранилища. Файл обратной связи всегда сохраняется под UUID внутри feedback.

Сохранить обычный контракт `--db` и `--json`, понятные ошибки и коды завершения. Rating и status валидируются. Недоступная ссылка на источник не мешает сохранить жалобу: сообщение может относиться именно к удалённому или повреждённому источнику; показать локальное предупреждение.

### 7.4. Разбор

Статусы: `new`, `triaged`, `planned`, `resolved`, `dismissed`. Переход сохраняет время и причину; исходное сообщение не переписывается. Resolved содержит ссылку на исправление или короткое описание результата проверки. Dismissed означает решение не менять систему с объяснением, а не удаление неудобного примера.

После первых 5–10 реальных задач владелец просматривает новые сообщения и выбирает несколько повторяющихся проблем. Это ориентир для разбора опыта, а не условие продолжения использования или автоматическое расписание.

## 8. Как обратная связь влияет на развитие

| Наблюдение | Первое действие |
| --- | --- |
| Агент не прочитал соседнюю строку | Уточнить шаблон чтения контекста, проверить на конкретном примере |
| Найденная запись неполная | Проверить источник и предложить исправленный draft владельцу |
| Релевантная запись не находится | Сохранить запрос и ожидаемый ID; проверить формулировки и индекс |
| Нужны точные фильтры проекта/периода | Добавить минимальный фильтр API с проверкой доступа |
| Ответ опирается на устаревшие данные | Исправить запись/источник и проверить механизм stale |
| Есть отказ или выдача данных вопреки меткам | Воспроизвести нарушение доступа и исправить приоритетно |
| Слишком много действий при работе | Упростить конкретный шаг интерфейса или добавить клиентскую команду |

Один неудовлетворительный ответ не является достаточным основанием для смены архитектуры поиска. Сначала определить, что именно не сработало: импорт, метаданные, поиск, чтение контекста или рассуждение модели. Улучшение проверяется на исходном примере и нескольких близких запросах, без обязательного запуска большого нового пилота.

## 9. Использование реальных данных

Владелец начинает с одного рабочего проекта и текущего механизма импорта. Не требуется заново размечать всю базу или собирать специальный большой корпус. Новые источники остаются unclassified до изменения метки.

При работе с внешней моделью используется external-профиль; в контекст попадают только явно разрешённые материалы. Для закрытых данных нужен настроенный локальный контур. Local-токен сам по себе не делает внешнюю модель локальной и не должен использоваться для обхода правил.

Массовое автоматическое сохранение разговоров и ответов не включается. Пользователь выбирает, что сохранить в feedback или предложить как новое знание. Если нет разрешённых источников для задачи, агент сообщает об ограничении доступных материалов и всё равно может помочь сформулировать вопросы к встрече, обозначив их как предложения.

## 10. Надёжность и проверки

Feedback сохраняется через временный файл и атомарную замену. Добавление и изменение статуса используют существующую блокировку записи. Исходное сообщение и история статусов сохраняются при переносе базы. Повреждённый feedback-файл не делает недоступными источники, знания или поиск: команды feedback показывают конкретную локальную диагностику.

Реализовать небольшие содержательные тесты:

- создание, чтение и смена статуса feedback с сохранением исходного текста;
- перенос папки базы и относительная независимость файлов;
- ошибки схемы и ограничение размера note/expected; предложенный предел — по 64 KiB;
- сохранение сообщения об отсутствующем source ID;
- отсутствие feedback в существующем поиске знаний и внешних HTTP-ответах;
- корректные CLI JSON-ответы и ошибки;
- прерывание записи не повреждает уже сохранённое сообщение.

Для шаблонов достаточно короткой проверки на известных примерах из эксплуатации, включая прежнюю ошибку с причиной в строке 4. Не вводить тесты, проверяющие точное совпадение формулировок LLM. Ранее принятые проверки хранения, доступа и MCP сохраняются; повторно расширять их только при изменении соответствующего кода или выявленной регрессии.

## 11. План реализации

1. Зафиксировать принятие текущей основы и добавить два переносимых шаблона.
2. Реализовать файловый FeedbackRepository и CLI владельца с небольшим набором тестов.
3. Добавить инструкцию повседневной работы: выбор шаблона, получение результата, сохранение полезной обратной связи.
4. Начать использовать систему на текущих рабочих задачах; сохранить первые конкретные примеры пользы и ошибок.
5. Выбрать следующий небольшой пакет изменений по обратной связи. Возможные направления — контекст вокруг цитаты, метаданные, фильтры или удобство клиентских команд.

## 12. Критерии готовности инкремента 4.1

- Пользователь может получить бриф к встрече и разбор решения через имеющийся MCP-клиент по двум понятным шаблонам.
- Результаты показывают источники фактов, отделяют оценки и обозначают пробелы покрытия.
- Не требуется новый LLM-провайдер, новая инфраструктура поиска или изменение уровней доступа.
- Владелец может сохранить короткий отзыв, найти его позже и отметить результат исправления.
- Feedback не попадает во внешнюю выдачу и не меняет знания автоматически.
- Есть инструкция и несколько реальных примеров использования с замечаниями пользователя; отсутствие идеальной оценки качества не блокирует дальнейшую эксплуатацию.

Основной показатель этого этапа — полезность в реальных задачах и возможность быстро исправлять конкретные проблемы. Численные показатели можно собирать позже, когда станет понятно, какие решения они должны поддерживать.
