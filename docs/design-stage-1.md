# Дизайн первого этапа персональной базы знаний

Импорт файлов, переносимое хранение и полнотекстовый поиск

| Документ | Версия | Дата | Статус |
| --- | --- | --- | --- |
| Дизайн реализации | 0.2 | 28 октября 2026 | Этап 1.1 реализован; ограничения описаны ниже |

Этот документ описывает первый рабочий этап базы знаний: как импортировать исходные файлы, сохранять их вместе с извлечённым текстом и находить нужные фрагменты. Результат этапа — локальная переносимая база и простой интерфейс командной строки. Извлечение выводов с помощью LLM и подключение агентов намеренно относятся к следующим этапам.

## 1. Цель и границы

Цель этапа — создать надёжную основу для данных из разных источников. Исходный файл остаётся доступным для проверки, а индекс поиска можно удалить и построить заново. На этом этапе система не пытается автоматически формировать окончательные факты или решения.

| Входит в этап | Не входит в этап |
| --- | --- |
| Импорт одного файла или каталога файлов | Автоматический импорт из Jira, Slack, GitHub и других сервисов |
| Хранение оригиналов и извлечённого текста | Извлечение знаний и ответов с помощью LLM |
| Метаданные источников, контрольные суммы, статусы обработки | MCP-сервер и интеграция с клиентами агентов |
| Полнотекстовый поиск и просмотр найденного фрагмента | Семантический поиск и отдельная векторная база |
| CLI для импорта, поиска, просмотра и пересборки индекса | Подготовка встреч и оценка решений |
| Зарезервированная метка доступа для будущих этапов | Передача данных внешним моделям |

Предположение реализации: первая версия предназначена для одного пользователя на локальной машине. Архитектуру не следует связывать с одной операционной системой или одной LLM-платформой.

## 2. Проектные решения

| Решение | Обоснование |
| --- | --- |
| Файлы — каноническое хранилище | Оригиналы и метаданные доступны обычными инструментами; перенос не требует экспорта из проприетарной базы. |
| SQLite FTS5 — поисковый индекс | Подходит для локального полнотекстового поиска; индекс является производным и перестраивается из файлов. |
| CLI — интерфейс MVP | Покрывает основные операции и позволяет позже добавить веб-интерфейс или MCP-адаптер поверх того же ядра. |
| Импорт не меняет оригинал | Система копирует исходный файл в базу и извлекает текст отдельно. |
| Неизвестные форматы сохраняются | Если текст нельзя извлечь, файл всё равно сохраняется с понятным статусом обработки. |

## 3. Основные сценарии

1.  Пользователь импортирует файл или каталог. Система сохраняет копии оригиналов, определяет формат, извлекает текст, записывает метаданные и обновляет поисковый индекс.

2.  Пользователь ищет фразу или набор слов. Система возвращает подходящие источники с типом, датой, кратким фрагментом и идентификатором записи.

3.  Пользователь открывает запись источника. Система показывает метаданные, статус извлечения, путь к оригиналу и извлечённый текст.

4.  Пользователь удаляет индекс или переносит базу. После запуска команды пересборки индекс восстанавливается из оригиналов, метаданных и сохранённого извлечённого текста.

## 4. Архитектура

Поток данных разделён на три части: неизменяемый оригинал, производный текст и поисковый индекс. Оригинал и метаданные являются архивом; извлечённый текст можно пересоздать из оригинала, если экстрактор ещё доступен; SQLite можно полностью пересоздать.

| Компонент | Ответственность | Данные |
| --- | --- | --- |
| CLI | Разбор команд и вывод результатов | Аргументы команд, форматированный текст/JSON |
| Импортёр | Обход пути, дедупликация и регистрация источников | Исходный файл, checksum, метаданные импорта |
| Экстрактор | Извлечение текста из поддерживаемых форматов | Текст, имя экстрактора и его версия |
| Хранилище файлов | Сохранение оригинала, sidecar-метаданных и текста | Обычные файлы в корне базы |
| Индексатор | Создание/обновление полнотекстового индекса | SQLite FTS5 |
| Поисковый модуль | Запрос к индексу, фильтрация и сниппеты | ID источника, совпадение и фрагмент текста |

Ключевое ограничение: CLI и будущие интеграции должны вызывать общие функции импорта и поиска. MCP, веб-интерфейс или конкретный LLM-клиент не должны содержать собственную логику доступа к индексам или файловому хранилищу.

## 5. Структура каталога базы

```text
knowledge-base/
  manifest.jsonl              # необязательный перечень всех source_id
  sources/
    <source_id>/
      source.json             # канонические метаданные записи
      original.<ext>          # точная копия исходного файла
      extracted.txt           # извлечённый текст, UTF-8
  index/
    search.sqlite             # перестраиваемый полнотекстовый индекс
  config/
    settings.json             # версия схемы и настройки экстракторов
```

Каждый импортированный файл получает отдельный каталог. Для каталогов-источников файлы импортируются по одному; структура исходного пути сохраняется в метаданных. Имена файлов не используются как идентификаторы, чтобы избежать конфликтов и небезопасных путей.

В MVP сами оригиналы считаются неизменяемыми. Если содержимое файла изменилось, создаётся новая запись источника. Точное совпадение SHA-256 при повторном импорте распознаётся как дубликат и не создаёт вторую копию; повторный импорт добавляет новый путь-алиас или обновляет дату последнего обнаружения.

## 6. Модель данных

### 6.1. Запись источника source.json

| Поле | Тип | Обязательно | Назначение |
| --- | --- | --- | --- |
| schema_version | строка | да | Версия формата метаданных. |
| source_id | UUID | да | Стабильный ID записи источника. |
| content_sha256 | строка | да | Контрольная сумма оригинала для поиска дубликатов. |
| original_name | строка | да | Имя файла при импорте. |
| source_type | строка | да | Например: file, transcript, ticket_export, code_snapshot. |
| mime_type | строка или null | да | Определённый или предоставленный тип содержимого. |
| imported_at | ISO 8601 | да | Дата и время первого импорта в UTC. |
| last_seen_at | ISO 8601 | да | Дата последнего повторного импорта/обнаружения. |
| origin_path | строка или null | да | Путь файла до копирования; информационное поле. |
| extractor | объект | да | Название экстрактора, версия, статус и сообщение ошибки. |
| access | строка | да | В MVP всегда unclassified; зарезервировано для будущей политики. |
| aliases | массив строк | да | Дополнительные исходные пути, по которым найден тот же файл. |

Идентификатор source_id — случайный UUID; content_sha256 используется для дедупликации, но не как публичный ID. Это позволяет позже хранить версии и ссылки на источник независимо от способа вычисления хэша.

### 6.2. Статусы обработки

| Статус | Значение | Поведение поиска |
| --- | --- | --- |
| pending | Запись создана, обработка не завершена | Не возвращается как текстовый результат |
| indexed | Текст извлечён и добавлен в индекс | Доступна в полнотекстовом поиске |
| unsupported | Файл сохранён, но формат не поддержан | Можно найти по метаданным и открыть оригинал |
| extraction_error | Экстрактор завершился ошибкой | Показывает ошибку; можно повторить обработку |
| empty_text | Экстракция завершилась без текста | Оригинал сохранён; в поиске содержимого не участвует |

## 7. Поддерживаемые форматы

Формат определяется по сигнатуре содержимого, расширению и доступным MIME-метаданным. Расширение само по себе не считается гарантией формата. Ошибочный или неизвестный формат не должен останавливать импорт остальных файлов.

| Приоритет | Форматы | Поведение в MVP |
| --- | --- | --- |
| Обязательные | TXT, Markdown, HTML, JSON, CSV, YAML, исходный код и другие UTF-8 текстовые файлы | Извлечь содержимое как текст; сохранить оригинал. |
| Желательные | PDF с текстовым слоем | Извлечь текст и сохранить оригинал. OCR сканов не входит в MVP. |
| Опциональные | DOCX, EML, типовые JSON/CSV-экспорты задач | Добавлять, только если экстрактор доступен без усложнения основного контура. |
| Не поддерживаются как текст | Изображения, аудио, видео, бинарные файлы, архивы без специальной обработки | Сохранить оригинал, поставить unsupported и вывести предупреждение. |

Для экспорта кода рекомендуется импортировать выбранные текстовые файлы или зафиксированный снимок репозитория, а не сканировать рабочую папку целиком. `.git`, зависимости, сборочные артефакты, секреты и большие бинарные файлы исключаются правилами импорта.

## 8. Процесс импорта

1.  Проверить, что входной путь существует и пользователь имеет право его читать. Если передан каталог, обходить его рекурсивно с учётом `.kbignore` и встроенных исключений.

2.  Сформировать перечень файлов и проверить ограничения по размеру. Ограничение на один файл задаётся конфигурацией; рекомендуемое начальное значение — 50 МБ.

3.  Для каждого файла вычислить SHA-256. Если такой checksum уже есть, не создавать копию; записать путь как alias и отметить повторное обнаружение.

4.  Для нового файла создать временный каталог записи, скопировать оригинал потоково, повторно проверить checksum и атомарно переименовать временный каталог в постоянный.

5.  Определить тип и запустить соответствующий экстрактор с лимитами времени и памяти. Не выполнять импортируемый код и не запускать макросы.

6.  Сохранить extracted.txt и обновить source.json со статусом и диагностикой. Если извлечение не удалось, оставить оригинал и записать понятный статус ошибки.

7.  Добавить или обновить запись в SQLite FTS5 после успешного сохранения файлов. Частично завершённая операция должна быть безопасна при повторном запуске.

8.  Показать сводку: импортировано, уже было, индексировано, неподдерживаемые файлы, ошибки.

Импорт каталога не должен быть одной большой транзакцией: ошибка одного документа не отменяет успешный импорт остальных. Повторный запуск должен продолжить обработку незавершённых записей.

## 9. Поиск

Поиск в MVP — полнотекстовый, без embeddings и генерации ответа. Индекс содержит извлечённый текст и ограниченный набор индексируемых метаданных: original_name, source_type и source_id. Фильтры применяются в SQLite по source_type, датам импорта и статусу.

| Параметр | Поведение |
| --- | --- |
| Язык | Запрос и документы могут быть на русском и английском. Используется Unicode-токенизация; морфологический поиск, синонимы и транслитерация не обещаются. |
| Ранжирование | Сначала полнотекстовая релевантность; при равной релевантности — более новый импорт. |
| Сниппет | Показывается короткий фрагмент с подсветкой совпавших терминов. По умолчанию до 240 символов. |
| Источник | Каждый результат содержит source_id, имя, source_type, imported_at и путь внутри базы. |
| Лимит | По умолчанию 10 результатов; пользователь может изменить лимит. |
| Отсутствие совпадений | Показать пустой результат, а не формулировать предполагаемый ответ. |

Система не утверждает, что найденный фрагмент является фактом. Поиск лишь показывает совпадения в сохранённых материалах; интерпретация и ответы по фактам относятся к последующим этапам.

## 10. Команды CLI

| Команда | Назначение | Пример результата |
| --- | --- | --- |
| kb init <path> | Создать структуру базы и конфигурацию. | Путь базы, версия схемы. |
| kb import <path> | Импортировать файл или каталог. | Сводка статусов обработки. |
| kb search <query> | Найти фрагменты с опциональными фильтрами. | Результаты с источниками и сниппетами. |
| kb show <source_id> | Показать метаданные, статус и пути файлов. | Карточка источника; при флаге --text — extracted.txt. |
| kb status | Показать число записей по статусам и состояние индекса. | Сводка базы, версия схемы, ошибки. |
| kb rebuild-index | Удалить и пересобрать индекс из сохранённых source.json и extracted.txt. | Число обработанных и пропущенных записей. |

Для автоматизации команды могут поддерживать `--json`; человекочитаемый вывод остаётся форматом по умолчанию. Код завершения ненулевой только при ошибке команды или неполной операции, требующей внимания.

## 11. Ошибки и восстановление

| Ситуация | Ожидаемое поведение |
| --- | --- |
| Недоступный входной путь | Не менять базу; показать путь и причину отказа. |
| Файл превышает лимит | Не копировать частично; отразить файл в итоговой сводке. |
| Неизвестный формат | Сохранить оригинал и метаданные, статус unsupported. |
| Ошибка извлечения текста | Сохранить оригинал, записать extractor error, продолжить каталог. |
| Остановка процесса во время импорта | Временные каталоги не считаются готовыми; следующая команда может очистить или продолжить их. |
| Индекс повреждён или удалён | Предложить/выполнить rebuild-index; канонические файлы не меняются. |
| Повторный импорт checksum | Не дублировать данные; обновить alias и last_seen_at. |

## 12. Безопасность и приватность

- База по умолчанию локальная. На первом этапе нет исходящих запросов к LLM или внешним сервисам.

- Метка access всегда создаётся со значением unclassified. Это подготовка схемы, а не полноценная система разграничения доступа.

- Импортируемый текст считается недоверенными данными. Он не выполняется как код; извлечение использует ограниченные ресурсы и не запускает макросы.

- Пути, имена файлов и архивные записи очищаются от path traversal и коллизий. Секреты не выводятся целиком в терминал по умолчанию.

- Резервная копия включает каталог sources и config. SQLite можно исключить или сохранить как ускоряющую копию, но не считать единственной копией базы.

- Если каталог синхронизируется внешним облачным сервисом, это решение остаётся за владельцем базы и должно учитывать содержимое оригиналов.

## 13. Нефункциональные требования

| Область | Требование этапа |
| --- | --- |
| Переносимость | Корневой каталог можно скопировать; после переноса `kb status` и `kb rebuild-index` восстанавливают поиск. |
| Надёжность | Ошибки отдельных файлов изолированы; импорт идемпотентен по checksum. |
| Производительность | На типовом ноутбуке 10 000 текстовых документов индексируются без отдельного сервера; число — целевой ориентир, подлежит измерению. |
| Наблюдаемость | Команда status показывает счётчики статусов и сообщения последних ошибок. |
| Расширяемость | Экстрактор — заменяемый компонент с названием и версией в метаданных. |
| Восстановимость | Поисковый индекс создаётся заново только из файлов базы; никаких скрытых обязательных облачных состояний. |

## 14. Приёмка этапа

- Можно создать новую базу и импортировать одиночный файл или каталог с вложенными папками.

- Текстовые файлы, CSV, JSON и PDF с текстовым слоем обрабатываются согласно объявленным возможностям; неподдерживаемые файлы не теряются.

- Повторный импорт того же содержимого не создаёт дубликаты.

- Поиск по словам на русском и английском возвращает релевантные фрагменты с идентификаторами источника.

- Каждый результат поиска можно связать с сохранённым оригиналом и extracted.txt.

- После удаления `index/search.sqlite` команда rebuild-index восстанавливает результаты поиска.

- Сбой извлечения одного файла не прерывает импорт остальных.

- CLI предоставляет команды init, import, search, show, status и rebuild-index.

- В MVP не вызываются внешние LLM и сетевые API.

## 15. Что отложено и открытые решения

| Вопрос | Предложение для MVP | Когда пересмотреть |
| --- | --- | --- |
| PDF со сканами | Сохранить, отметить unsupported/empty_text; OCR не делать. | Если значительная доля документов — сканы. |
| Векторный поиск | Не внедрять до оценки качества FTS на реальных запросах. | После накопления примеров неудачного поиска. |
| Веб-интерфейс | Начать с CLI. | Когда ручной CLI станет барьером ежедневного использования. |
| Автообновление источников | Повторный импорт по файлу/каталогу вручную. | Когда появятся стабильные коннекторы и требования к расписанию. |
| Пароль/шифрование базы | Опора на шифрование диска ОС; отдельный криптоконтейнер не включать в MVP. | До подключения синхронизации или совместного доступа. |
| Формат упаковки/экспорта | Обычная папка; добавить команду экспорта архива при необходимости. | Перед первой миграцией между машинами. |

## 16. Итоговый результат

По завершении первого этапа у пользователя есть локальная файловая база с неизменёнными оригиналами, метаданными происхождения, сохранённым извлечённым текстом и пересоздаваемым полнотекстовым индексом. Через CLI можно импортировать данные, находить фрагменты, открывать источник и восстанавливать индекс. Эта база становится проверяемым фундаментом для последующего извлечения знаний и подключения локальных и внешних агентов.

## 17. Реализация этапа 1.1: надёжность импорта и индекса

CLI сообщает результат для каждого обработанного файла и продолжает импорт после локальной ошибки. Параметр `--json` выдаёт JSON в stdout; обычный режим показывает краткие сводки, а `--verbose` добавляет технические детали ошибок. Лимит одного файла задаётся валидируемым `config/settings.json`. Операции импорта и пересборки используют эксклюзивную блокировку базы с ожиданием до 30 секунд.

Оригиналы и `source.json` остаются каноническими. Импорт потоково хэширует вход и копию, извлекает текст из копии и сохраняет фактический относительный путь оригинала. Для старых записей без `original_relative_path` путь восстанавливается из находящегося рядом файла оригинала. Каталоги и файлы, совпавшие с glob-правилами `.kbignore`, пропускаются; символьные ссылки при обходе каталогов не разыменовываются.

`status --verify` проверяет целостность SQLite и наличие записей источников в индексе. `rebuild-index` строит соседнюю временную базу, проверяет её до замены и оставляет прежний индекс на месте при ошибке. Тесты находятся в `tests/KnowledgeBase.Tests` и запускаются командой `dotnet test KnowledgeBase.slnx`; GitHub Actions выполняет restore, build и test на Windows, Linux и macOS.

Ограничения MVP: PDF обрабатываются только при наличии текстового слоя, OCR отсутствует; `.kbignore` не является сканером секретов, поэтому чувствительные файлы нужно исключать явно. SQLite является производным индексом и может потребовать пересборки после аварийного завершения обновления.
