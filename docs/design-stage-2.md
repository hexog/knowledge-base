## 1. Оценка этапа 1.1

Изменения существенно улучшили основу: копия оригинала проверяется по SHA-256; ошибки импорта отражаются пофайлово; настройки размера применяются; оригинальный путь хранится в метаданных; добавлены блокировка операций, правила исключений, временный индекс при пересборке и тестовый проект. Это позволяет переходить к проектированию структурированных знаний после устранения оставшихся проблем целостности.

Обзор статический: код и тесты прочитаны на указанном коммите; сборка, тесты и CI самостоятельно не запускались. Сообщение агента о 10 успешных тестах и незапущенной локально матрице ОС принято как его отчёт.

## 2. Цель и границы этапа 2

Цель — создавать из импортированных источников небольшие структурированные записи и давать человеку возможность проверить их по конкретным фрагментам. Записи и подтверждения хранятся в переносимых файлах; индекс остаётся производным.

Результат: пользователь импортирует источник, создаёт или получает предложенные черновики, открывает каждый вместе с подтверждениями, исправляет и принимает либо отклоняет его, затем ищет принятые записи и переходит к источникам.

В объём входят ручное создание и проверка записей, подключаемый локальный экстрактор предложений, ссылки на фрагменты, жизненный цикл черновика и FTS-поиск по знаниям. Внешние LLM, MCP, автоматическое принятие записей, полноценный контроль доступа, векторный поиск и автоматическое разрешение противоречий остаются отдельными этапами. До появления шлюза не считать поле `access` механизмом защиты от передачи данных.

## 3. Предварительные исправления этапа 1.1

1. В `status --verify` проверять SHA-256 оригинала, наличие и хэш извлечённого текста, соответствие FTS тексту и метаданным, единственность строки на ID. Сообщать каждую проблему с ID и категорией. Для больших архивов явная глубокая проверка может быть отдельным режимом.
2. Если у `indexed` нет извлечённого текста или он не соответствует сохранённому хэшу, пересборка завершается ошибкой и сохраняет рабочий индекс. Для повреждённых метаданных действует тот же принцип.
3. Поиск по отсутствующему индексу при наличии источников сообщает о необходимости пересборки; не выдаёт молчаливо пустую выдачу. Пустой индекс создаётся при `init` новой базы.
4. Заменить tuple результата пересборки именованным DTO; добавить тесты JSON и кодов завершения. `status --verify` возвращает ненулевой код при обнаружении нарушений.
5. Запретить включение корня базы во входной каталог импорта или явно исключить его при обходе. Ограничить размер извлечённого текста и документировать использование памяти. Чтение метаданных сделать без побочных записей; миграцию выполнять отдельно под блокировкой.

Сначала добавить регрессионные тесты этих условий. Не начинать автоматическое извлечение знаний, пока проверка источников и пересборка не дают достоверную диагностику.

## 4. Модель данных

Каталоги базы:

```text
sources/<source_id>/source.json, original.*, extracted.txt
knowledge/drafts/<record_id>.md
knowledge/reviewed/<record_id>.md
knowledge/archived/<record_id>.md
```

Поисковый SQLite индекс — локальный производный кеш вне переносимой папки; он восстанавливается из перечисленных канонических файлов. Подробнее — в [инструкции по синхронизации](database-sync.md).

Каждая запись — UTF-8 Markdown с YAML front matter и телом. ID — UUID, стабильный при редактировании и перемещении между статусами. Версия схемы задаётся явно. Обязательные поля:

```yaml
schema_version: 1
id: 63f38374-0706-44a9-8b17-1e365a0551a2
type: decision
kind: source_claim
status: draft
title: Обработка очереди выделяется в сервис
project: payments
created_at: 2026-10-28T12:00:00Z
updated_at: 2026-10-28T12:00:00Z
valid_from: null
valid_to: null
access: unclassified
source_refs:
  - source_id: 4aef754c-a797-4218-8e9f-94f5b5174c61
    text_sha256: "<sha256 извлечённого текста>"
    start_line: 12
    end_line: 14
    quote: "Подтверждающий фрагмент"
```

Типы: `fact`, `decision`, `meeting`, `task`, `risk`, `question`. `kind` различает `source_claim` и `inference`. Утверждение требует хотя бы одного подтверждающего фрагмента; вывод требует ссылку на исходные материалы и явную формулировку как оценку. `project` и период действия необязательны. Даты действия не выводятся автоматически при отсутствии данных.

Диапазон строк — 1-based, включительный, в сохранённом `extracted.txt`; счёт ведётся после нормализации переносов строк к LF при извлечении. Хэш привязывает диапазон к версии текста. При изменении текста ссылки становятся устаревшими и требуют повторной проверки. PDF на этом этапе цитируется по извлечённому тексту, страницы не обещаются. Хранить короткую цитату как контроль читаемости, а не как единственное доказательство. Для разных форматов позднее можно добавить локаторы страниц или временные метки через версионируемый тип локатора.

Уровень доступа черновика наследуется от источника. При нескольких источниках действует самый строгий результат: `local_only`, затем `unclassified`, и только если все источники `external_allowed` — `external_allowed`. В этом этапе новые источники обычно `unclassified`. При изменении метки источника производные записи должны переоцениваться при выдаче; явное разрешение на запись не может переопределить более строгий источник. Фактическое принудительное применение внешнего доступа будет реализовано в шлюзе следующего этапа.

## 5. Создание и проверка

1. Пользователь выбирает источник и запускает создание черновиков вручную или через локальный адаптер модели. Адаптер получает только явно выбранный извлечённый текст; сетевой вызов по умолчанию отсутствует.
2. Модель возвращает структурированный JSON с типом, заголовком, утверждением, диапазоном и цитатой. Код проверяет схему, существование источника, границы и точное совпадение цитаты с выбранным текстом. Непроверенный вывод сохраняется только как черновик с ошибкой валидации, либо отклоняется с диагностикой.
3. Каждый черновик сохраняется атомарно. Повторная генерация не перезаписывает принятые записи; уникальный идентификатор операции связывает предложения одного запуска. Совпадения предлагаются человеку как возможные дубликаты, без автоматического слияния.
4. `review` показывает текст записи и источник с контекстом. Человек правит содержание и выбирает `accept` или `reject`; перед принятием программа проверяет ссылки и фиксирует время проверки и проверенные хэши. Принятие без явного подтверждения просмотра источника запрещено в интерактивном режиме. Для CLI-автоматизации требуется явное подтверждение и перечисление проверенных ссылок; сам флаг не доказывает, что человек прочитал данные.
5. При изменении источника, извлечённого текста или утверждения статус проверки становится устаревшим и запись требует повторной проверки. Отклонённый черновик архивируется с причиной по желанию; незаметная замена проверенной записи запрещена.

Противоречия не разрешаются автоматически: запись может содержать `related_records` со связью `conflicts_with` или `supersedes`; обе версии видимы с датами и источниками. Статус `reviewed` означает проверку человеком, а не гарантию истинности.

## 6. Интерфейс и поиск

Предлагаемые команды:

- `kb record draft --source <id>` — создать черновик вручную; `kb extract --source <id> --provider local` — предложить черновики через настроенный локальный адаптер.
- `kb record list --status draft` и `kb record show <id> --sources` — список и просмотр записи с подтверждениями.
- `kb record edit <id>` — открыть локальный редактор с последующей проверкой схемы и атомарным сохранением.
- `kb record accept <id> --confirm-sources` / `kb record reject <id>` — явный переход состояния; при устаревших или недоступных ссылках принятие запрещено.
- `kb search <query> --scope sources|knowledge|all --record-status reviewed` — поиск с указанием типа результата, ID, статуса и источников. По умолчанию знания показываются только проверенные; черновики доступны явным фильтром.

Добавить в SQLite отдельные таблицы метаданных и FTS для записей. Канонические Markdown-файлы — источник истины. `rebuild-index` строит обе части во временной базе и заменяет индекс только после успешной проверки. Поиск результатов по знаниям не должен скрывать конфликтующие записи. Ошибки YAML и отсутствующие ссылки выводятся в диагностике с путём; повреждённая запись не исчезает молча.

## 7. Адаптер извлечения

Определить интерфейс `IKnowledgeExtractor` с входом: ID источника, хэш и текст, параметры задания; выходом: версия схемы, кандидатные записи, ссылки на точные фрагменты, диагностические ошибки. Хранить имя и версию адаптера и модели, время запуска и ID операции; секреты и полный запрос в метаданных не хранить. Текст источника считать данными, а инструкции в нём не выполнять.

Первый адаптер — локальный процесс или локальный API с явно заданным адресом и отключённой сетью по умолчанию. Ограничить размер входа, время, число кандидатов и размер ответа; ошибки адаптера не меняют проверенные знания. Разделение больших документов на фрагменты сохраняет глобальные номера строк. Конкретный движок не является частью формата данных.

## 8. Надёжность и миграция

Источники версии 1 остаются читаемыми; перед внедрением хэшей текста предусмотреть явную миграцию с резервной копией метаданных, блокировкой и отчётом. Миграция не изменяет оригиналы. Записи сохраняются через временный файл в том же каталоге и атомарную замену; между статусами операции должны быть восстанавливаемыми после прерывания. Для одного пользователя достаточно существующей блокировки записи, если она распространяется на импорт, миграцию, редактирование, переход статуса и пересборку. Чтение не должно незаметно менять файлы.

## 9. Проверки и критерии приёмки

- Ручной черновик создаётся, редактируется, принимается и находится по содержимому; источники и диапазоны открываются в контексте.
- Неверный ID, диапазон, цитата или изменённый текст блокируют принятие и дают конкретную диагностику.
- Источник, утверждение и вывод различимы; вывод модели не становится подтверждённым фактом автоматически.
- Конфликтующие утверждения и история статусов видимы; генерация не перезаписывает проверенные записи.
- Метка вычисляется из всех источников с безопасным значением по умолчанию; внешняя передача на этом этапе не реализована.
- После удаления индекса полная пересборка восстанавливает поиск по источникам и записям. При ошибке построения прежний индекс сохраняется.
- Тесты покрывают пустой и повреждённый источник, устаревшую цитату, ошибку генератора, дедупликацию предложений, изменение метки, прерывание сохранения и повреждённый индекс. Добавить тесты CLI JSON и проверки после переноса папки на другой путь.
- CI выполняет сборку и тесты на Windows, Linux и macOS. Поддержка платформ считается подтверждённой после успешного прохождения матрицы, а не по наличию конфигурации.

## 10. Порядок работ

1. Исправления целостности этапа 1.1 и регрессионные тесты.
2. Схема файлов и миграция, ручные черновики и проверка ссылок.
3. Поиск, пересборка и переходы статусов с тестами восстановления.
4. Локальный адаптер извлечения и тесты на контролируемых примерах.
5. Приёмка на небольшой выборке реальных источников: точность цитат, полезность предложений, пропущенные и ложные утверждения.
