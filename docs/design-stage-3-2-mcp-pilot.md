## 1. Исходное состояние

В [коммите af297dd](https://github.com/hexog/knowledge-base/commit/af297dd8199998ce68d683992d366747e3883260) исправлены последние два замечания обзора: ограничение 1 000 кандидатов применяется после проверки доступности записей, а тест потокового HTTP 413 отправляет корректный JSON небольшими чанками без Content-Length. Добавлен регрессионный сценарий с 1 001 закрытой проверенной записью и двумя разрешёнными.

Новых блокирующих замечаний в этом изменении статически не обнаружено. Это заключение относится к просмотренным изменениям, а не является гарантией отсутствия дефектов во всём проекте. Сборка и тесты в окружении обзора независимо не запускались: `dotnet` отсутствует. Успешность CI не подтверждена. Перед пилотом нужно получить зелёный Release-прогон существующего набора, включая HTTP-тесты, на поддерживаемых платформах.

Дальнейшая задача — проверить полезность базы в работе реального агента, сохранив существующую границу доступа.

## 2. Цель и ожидаемый результат

Подключить один MCP-совместимый агент к базе знаний через отдельный адаптер. Агент должен находить проверенные разрешённые записи, читать их с цитатами, открывать диапазон источника и, после отдельного включения записи, предлагать черновики без автоматического принятия.

Результат этапа:

- отдельный запускаемый MCP-процесс для локального клиента;
- четыре инструмента с явными схемами входов и выходов;
- вызовы существующего HTTP API с отдельным клиентским токеном;
- тесты всей цепочки MCP → HTTP → файловая база;
- инструкция подключения одного выбранного клиента и отчёт пилота с проверяемыми примерами.

На этом этапе не требуется новая LLM внутри сервера, отдельная система прав, семантический поиск, новые типы импорта, удалённый MCP-хостинг или автоматическая подготовка встреч на стороне базы. Бриф и ответы составляет подключённый агент из полученных материалов.

## 3. Архитектура

Путь запроса: MCP-клиент запускает `KnowledgeBase.Mcp` через stdio; адаптер вызывает HTTP-шлюз на loopback; шлюз применяет действующие правила доступа, проверки версий, аудит и журналирование draft.

Новый проект `src/KnowledgeBase.Mcp` содержит:

| Компонент | Ответственность |
| --- | --- |
| MCP host | Протокол, регистрация инструментов, жизненный цикл и отмена |
| GatewayClient | Фиксированные HTTP-маршруты, bearer-токен, лимиты и обработка ответов |
| Tool handlers | Проверка аргументов и преобразование DTO между MCP и HTTP |
| Конфигурация | Endpoint, режим записи, таймауты и получение токена |

Адаптер не читает sources, knowledge, SQLite, registry или server state напрямую. Не ссылаться на Core ради обхода HTTP: транспортная интеграция должна проходить те же проверки, что и HTTP-клиент. DTO можно держать в проекте адаптера; общий пакет контрактов вводить только если он действительно уменьшит дублирование, не связывая клиент с внутренним хранилищем.

Для реализации использовать официальный C# SDK MCP; точную совместимую стабильную версию закрепить в проекте после проверки с выбранным клиентом. SDK обрабатывает согласование версии протокола; собственный JSON-RPC и ручной handshake не реализовывать. Официальный SDK поддерживает stdio и обычный .NET hosting; для первого адаптера достаточно пакета `ModelContextProtocol`. См. источники в разделе 14.

## 4. Транспорт и конфигурация

MVP использует только stdio: процесс запускает MCP-клиент на той же машине, где доступен HTTP-шлюз. Это подходит для локального агентского приложения, даже если его модель работает у внешнего провайдера. Для облачного клиента без возможности запустить локальный процесс понадобится отдельный транспорт и развёртывание — это другой этап.

Упаковка — отдельный .NET tool с командой `kb-mcp`, либо опубликованный DLL с эквивалентным запуском. Пример конфигурации процесса:

```text
KB_MCP_GATEWAY_URL=http://127.0.0.1:8765
KB_MCP_GATEWAY_TOKEN=<секрет клиента шлюза>
KB_MCP_ENABLE_DRAFTS=false
KB_MCP_HTTP_TIMEOUT_SECONDS=15
```

Токен не передаётся аргументом командной строки, параметром инструмента или результатом MCP. Значения из примера не сохранять в репозитории. В инструкции объяснить передачу секрета через защищённую конфигурацию выбранного host/окружение процесса без вывода в логи.

Endpoint задаёт владелец один раз при старте. Для MVP разрешены только числовые loopback-адреса; запретить userinfo, query и fragment в base URL. Не принимать URL, HTTP-заголовки и пути от модели. Отключить автоматические redirects и системный proxy для обращения к loopback, чтобы токен не ушёл на другой адрес. Только фиксированные `/v1/...` маршруты.

В stdout идут только протокольные сообщения MCP. Диагностика направляется в stderr; токен, запросы, тело знаний, цитаты и HTTP response body не логируются. Успешный запуск не печатает приветствие в stdout. При EOF stdin и штатном завершении клиентского процесса адаптер отменяет активные запросы, освобождает ресурсы и завершается.

Одна конфигурация процесса использует один token/client ID. Профиль не задаётся в MCP-параметрах. Для local и external при необходимости создаются отдельные конфигурации и токены, без переключения профиля внутри инструмента.

## 5. Контракты инструментов

Публичные имена: `search`, `get_record`, `get_source_text`, `draft_record`. Во всех схемах запретить неизвестные поля. Идентификаторы — UUID, строки и размеры ограничены до отправки HTTP. Проверки адаптера улучшают диагностику, но окончательное решение принимает шлюз.

| Инструмент | Аргументы | HTTP-вызов | Результат |
| --- | --- | --- | --- |
| search | query, limit=5, cursor=null | POST /v1/search | Разрешённые знания со сниппетами и цитатами, cursor и policy_revision |
| get_record | id | GET /v1/records/{id} | Актуальная версия записи, kind, status, title, body и citations |
| get_source_text | source_id, start_line, end_line | GET /v1/sources/{id}/text | Имя источника, диапазон и разрешённый текст |
| draft_record | idempotency_key, title, body, citations | POST /v1/drafts | Квитанция создания draft с ID записи и операции |

`search` ищет знания, которые предоставляет текущий endpoint; поиск произвольных оригиналов и выбор скрытых статусов не обещаются. Не добавлять локальный scope или фильтр, который шлюз не поддерживает. `get_source_text` получает только диапазон, разрешённый gateway; путь к файлу модели не выдаётся.

Лимиты совпадают с текущим API: query до 512 символов, limit 1–50; диапазон до 200 строк и 64 KiB текста; draft body до 64 KiB, 1–10 цитат. Idempotency-Key — 1–128 ASCII-символов из набора, разрешённого сервером. Размер JSON draft не превышает 1 MiB. Для title применить дополнительный клиентский предел 512 символов; не сокращать строку автоматически.

Для draft каждая цитата содержит source_id, start_line, end_line и quote; диапазон включительный, строки нумеруются с 1. Текущий gateway создаёт `fact` / `source_claim`; адаптер не принимает параметры type/kind/project, пока API явно их не поддерживает. Не имитировать эту возможность формированием произвольного Markdown.

### 5.1. MCP-результаты

Каждый инструмент объявляет inputSchema и outputSchema с объектом результата. Использовать structuredContent и текстовое JSON-представление того же результата для совместимости клиентов; не добавлять второе самостоятельное резюме моделью.

Единая оболочка:

```json
{
  "ok": true,
  "data": {
    "id": "d410ef72-887b-42b5-ad0c-c1b0fde53fa0",
    "status": "reviewed",
    "kind": "source_claim",
    "version": "<content_sha256>",
    "citations": []
  }
}
```

Это иллюстрация оболочки; полноценные схемы задаются для каждого инструмента. Пустые citations в примере не отменяют серверных требований для внешней выдачи. Успешный payload передаётся без изменения утверждений и цитат. HTTP header `X-Request-Id` переносится отдельным полем gateway_request_id для корреляции диагностики.

Ошибки схемы MCP/неизвестного инструмента обрабатываются протоколом SDK. Ошибка уже выполняемого вызова возвращается как результат инструмента с isError=true и безопасной структурой `ok: false`, `error.code`, `retryable`, `outcome_unknown`, при наличии — gateway_request_id. Ни токен, ни stack trace, ни локальные пути в результат не попадают.

### 5.2. Аннотации и включение записи

Для трёх инструментов чтения объявить readOnlyHint=true. Для draft — readOnlyHint=false, destructiveHint=false; idempotentHint=true корректен только потому, что одинаковые аргументы включают один и тот же idempotency_key. Аннотации помогают клиенту, но не являются механизмом разрешений.

По умолчанию draft_record не регистрируется в tools/list и не принимается через tools/call. Для включения владелец задаёт enable_drafts=true и выдаёт отдельный токен со scope draft. Опция сама по себе не даёт права: при недостаточном scope сервер возвращает отказ. Перечень инструментов фиксирован на время процесса; после изменения конфигурации процесс перезапускается.

Никаких инструментов accept, access set, client create, shell или запуска экстрактора в адаптере нет. Принятие знания и изменение меток выполняет владелец локально.

## 6. Ошибки, повторы и cursor

На первом этапе не выполнять скрытые автоматические повторы HTTP. Агент получает предсказуемый код и может повторить действие по явному контракту. Это особенно важно для одноразовых cursor и неоднозначного исхода записи.

| Ситуация | Код инструмента | Действие клиента |
| --- | --- | --- |
| 401 | unauthorized | Остановить вызовы; владелец проверяет токен |
| 403 | forbidden | Не менять профиль и не пробовать обход |
| 404 | resource_unavailable | Не предполагать, существует ли закрытый объект |
| 400 / 413 | invalid_request / request_too_large | Исправить аргументы или уменьшить запрос |
| 409 retry_required | retry_required | Для поиска начать с cursor=null и не смешивать прежние страницы с новым поиском |
| 409 idempotency_conflict | idempotency_conflict | Проверить операцию; не создавать новый ключ автоматически |
| 409 operation_recovery_required | operation_recovery_required | Передать владельцу ID операции/запроса без содержимого |
| 429 | rate_limited | Повторить позже, без автоматического цикла |
| 503 | service_unavailable | Повторить позже; для draft сохранить тот же ключ |
| Потерян ответ/таймаут draft | outcome_unknown | Повторить исходные аргументы с тем же ключом |
| Невалидный HTTP JSON/схема | gateway_protocol_error | Не показывать сырой ответ; сохранить безопасную диагностику |

Сетевой отказ при draft или HTTP 503 после сохранения не доказывает отсутствие записи. Адаптер всегда сохраняет/возвращает клиенту уже известный ключ операции; новый ключ означает новую операцию. JSON-RPC request ID не использовать как Idempotency-Key: он может меняться при повторе и перезапуске.

Cursor — непрозрачный токен gateway. Адаптер не разбирает, не кеширует результаты страниц и не переиспользует cursor автоматически. Если ответ страницы потерян, прежний cursor мог быть потреблён: клиент начинает поиск заново. При недоступности шлюза адаптер не отдаёт сохранённые документы из локального кеша.

Отмена MCP-вызова передаётся в HttpClient. Для отменённого draft результат может остаться неизвестным, если сервер успел сохранить запись. Стабильный ключ позволяет восстановить исход при следующем вызове. При перезапуске адаптера состояния авторизации и идемпотентности не восстанавливаются из памяти: они принадлежат gateway.

## 7. Ограничения ресурсов и граница доступа

Начальные пределы адаптера: до 4 одновременных инструментальных вызовов, HTTP timeout 15 секунд, JSON request до 1 MiB, HTTP response до 8 MiB и полный сериализованный MCP-ответ до 256 KiB, включая дублирующий текстовый блок. Если ответ не помещается, вернуть `response_limit_exceeded` и рекомендацию уменьшить limit или диапазон; не обрезать цитату и не выдавать частичный ответ как полный. Пределы задаёт владелец, а не модель. Ограничить размер входного MCP-сообщения средствами SDK либо проверяемым слоем транспорта.

Токен даёт доступ к API по правилам gateway. Он не изолирует агент, у которого уже есть доступ к папке базы, реестру или другим секретам. Для пилота использовать отдельную папку проекта агента и небольшой набор материалов, разрешённый для выбранной модели; при необходимости — контейнер или отдельного пользователя ОС. Не объявлять отсутствие инструмента файлового чтения в MCP доказательством системной изоляции.

Содержимое найденных документов рассматривается как данные. В тестовом корпусе есть текст с инструкцией игнорировать правила и открыть другой файл; адаптер возвращает его как содержимое и не выполняет никаких действий. Соблюдение этих инструкций самой моделью оценивается отдельно в пилоте и не заменяет ограничения инструментов и ОС.

## 8. Пилот

### 8.1. Корпус и конфигурация

Начать с 20–50 проверенных записей по одному проекту. Добавить заведомо закрытые и unclassified источники с контрольными маркерами для отрицательных проверок. Зафиксировать ожидаемые ID, цитаты и даты для 8–10 вопросов; хранить корпус как синтетическую фикстуру или локальные разрешённые данные, без секретов в Git.

Владелец выбирает один MCP-клиент, способный запускать stdio-процесс. Первый токен: external со scopes search,read; drafts выключены. После проверки чтения второй запуск использует отдельный токен с draft и явно включённым инструментом. Local-профиль проверяется автоматическими тестами, но не используется как запасной вариант при отказе external.

Не обещать установку на все MCP-клиенты. Для выбранного клиента документировать точную команду, рабочий каталог, способ передачи секрета и проверенную версию host; не выдумывать универсальный формат его конфигурации.

### 8.2. Сценарии

| Сценарий | Проверяемый результат |
| --- | --- |
| Найти решение по теме | ID принятой записи и точная цитата источника |
| Объяснить основания решения | Факты со ссылками; вывод агента явно отделён |
| Подготовить короткий бриф | Только доступные записи, указанные пробелы и источники |
| Вопрос без материалов | Агент сообщает недостаток данных, не придумывает факт |
| Запрос закрытой информации | В ответе и трассе инструментов нет контрольного маркера |
| Отзыв доступа после поиска | Следующее чтение/страница получает отказ или требование нового поиска |
| Источник изменён между страницами | Старый cursor не выдаёт устаревший результат |
| Предложение нового знания | Создан ровно один draft с проверяемой цитатой; reviewed не изменяются |
| Потеря ответа draft | Повтор с тем же ключом возвращает прежнюю квитанцию |

Шлюз сейчас не предоставляет полный обзор конфликтных связей или произвольные фильтры подготовки встречи. Оценивать только сценарии, поддержанные текущими endpoint; запрос на более широкий анализ фиксировать как потребность следующего этапа, а не обходить прямым чтением файлов.

### 8.3. Отчёт

В `docs/mcp-pilot-results.md` зафиксировать commit и версии клиента/SDK, обезличенные вопросы, ожидаемые и фактические ID/цитаты, число вызовов, задержку и замечания пользователя. Для безопасности — ноль закрытых маркеров и ноль изменений принятой базы. Для полезности — целевой минимум 8 из 10 заранее определённых вопросов с корректной опорой; результаты неуспешных вопросов сохранять с причинами. Это продуктовая оценка маленькой выборки, а не статистическая гарантия качества LLM.

Полные трассы с реальными данными по умолчанию не коммитить. Зафиксировать, какие сценарии выполнены человеком, какие автоматизированы, какие не проверены.

## 9. Автоматические проверки

### 9.1. Контракты

Проверить tools/list, четыре input/output schema, запрет неизвестных полей, ограничения чисел и размера, валидацию UUID, отсутствие draft в режиме чтения. Вызов незарегистрированного draft не должен обращаться к HTTP.

Проверить точное преобразование DTO в snake_case API, сохранение source_id, версии, диапазона и цитаты; mapping 401/403/404/409/413/429/503, пустых и повреждённых ответов. В structuredContent и текстовом блоке не должно быть разных данных.

### 9.2. Полная цепочка

Запускать настоящий gateway с временной базой и отдельный MCP-процесс, подключаясь SDK-клиентом по stdio. Проверить чтение, пагинацию, отзыв, stale, повреждение источника, создание draft и replay после перезапуска адаптера. Запросы проходят HTTP; тест не вызывает Core вместо шлюза.

Для сценария потерянного ответа использовать контролируемую точку разрыва соединения или тестовый прокси на loopback, а не случайную задержку. Проверить один ID draft и неизменную квитанцию. Дополнительно проверить отмену, отсутствие записей до отправки и неизвестный исход после фиксации.

### 9.3. Процесс и секреты

Проверить чистый stdout, завершение при EOF, отсутствие зависших процессов, ограничение ответа и корректную отмену. Убедиться, что bearer-токен и закрытые маркеры отсутствуют в MCP-ошибках и stderr; redirects и произвольные endpoint из аргументов инструмента отвергаются. Внутренние тесты используют управляемые потоки, а отдельный процесс нужен для проверки stdio и жизненного цикла.

Существующие HTTP-регрессии сохраняются. Сборка и тесты должны пройти в чистом Release на Windows, Linux и macOS. Зафиксировать точную зависимость SDK; не обновлять её автоматически внутри приёмочного прогона.

## 10. План реализации

1. Подтвердить зелёный CI базового коммита, выбрать один клиент пилота и закрепить версию SDK.
2. Создать проект MCP и GatewayClient, конфигурацию и протокольный запуск без инструментов записи.
3. Добавить три инструмента чтения, схемы и mapping ошибок; пройти контрактные и сквозные тесты.
4. Провести пилот чтения и исправить обнаруженные интеграционные проблемы.
5. Добавить draft_record за явным флагом, стабильный ключ и тест потери ответа/replay.
6. Провести пилот записи, подготовить инструкцию запуска и отчёт о результатах.

## 11. Критерии приёмки

- Проверенные исправления этапа 3.1 не регрессировали; CI поддерживаемых ОС зелёный.
- Один реальный MCP-клиент запускает адаптер и получает три инструмента чтения без токена в модели или логах.
- External выдача совпадает с разрешениями HTTP API; нет прямого доступа адаптера к файлам базы или автоматического повышения профиля.
- Все фактические ответы пилота имеют проверяемые источники; предположения агента отделены от фактов.
- Cursor, отзыв, ошибки и отмена обрабатываются по контракту, без скрытого кеша знаний.
- Draft включается явно, всегда остаётся черновиком; повтор после потери ответа или перезапуска создаёт единственную запись.
- Документация содержит фактическую конфигурацию выбранного клиента, ограничения и процедуру отзыва токена.
- Есть отчёт пилота с результатами, открытыми вопросами и решением о следующем расширении по наблюдениям.

После приёмки можно расширять подготовку встреч и оценку решений: добавлять недостающие фильтры, связи и шаблоны по результатам пилота. Потребность в семантическом поиске определять по конкретным неудачным запросам, а не включать его автоматически в интеграционный этап.

## 12. Изменения данных

Форматы sources и knowledge в этом этапе не меняются. MCP не создаёт собственную базу, индекс, историю или журнал идемпотентности. Секрет и параметры адаптера не включаются в переносимый архив. HTTP-квитанции и аудит остаются ответственностью gateway; пилотный отчёт не становится источником фактов автоматически.

## 13. Основные решения

| Решение | Причина |
| --- | --- |
| Stdio для первого MCP-клиента | Минимальный способ локального подключения без второго сетевого сервера |
| HTTP как единственный доступ к базе | Сохраняет существующие проверки и журналирование |
| Один профиль на процесс | Убирает переключение полномочий моделью |
| Чтение до записи | Позволяет отдельно оценить полезность поиска и корректность изменения базы |
| Стабильный ключ draft | Позволяет восстановить неизвестный исход без дубликата |
| Нет скрытых повторов и кеша знаний | Сохраняет прозрачную семантику cursor и отзыва |
