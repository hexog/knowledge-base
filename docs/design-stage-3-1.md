## 1. Цель и ожидаемый результат

Сделать шлюз пригодным для подключения первого реального агента: проверить авторизацию через HTTP, устранить ошибки повторного создания черновиков и конкурентных операций, обеспечить безопасную миграцию проверенных знаний и предсказуемое восстановление после сбоя.

По завершении этапа два клиента с профилями local и external работают через HTTP с одной переносимой базой. External получает только явно разрешённые актуальные данные. Повтор запроса создания черновика не создаёт дубликат после потери ответа или перезапуска. Медленный клиент не блокирует локальную работу владельца. Миграция не превращает изменённое утверждение в проверенное.

В объём входят исправления Core, Server и CLI, HTTP-интеграционные тесты, сценарии прерываний и документация эксплуатации. MCP-адаптер, генерация ответов, облачный хостинг и новые источники данных в этап не входят.

Заявленные агентом 28 тестов, сборка и smoke-проверка `401` не заменяют приёмку всех HTTP-маршрутов. При обзоре сборка и тесты независимо не запускались; результат CI не подтверждён.

## 3. Инварианты

1. Профиль и scopes определяются серверным реестром. Поля запроса не повышают права.
2. External не получает draft, stale, archived, неразмеченные или закрытые данные, включая цитаты, имена, ссылки и ошибки.
3. Статус reviewed сохраняется при миграции только после проверки прежнего снимка.
4. Пара client ID + Idempotency-Key обозначает одну операцию создания и один ID знания.
5. HTTP-ошибка после сохранения файла не означает, что файл отсутствует. Повтор с тем же ключом восстанавливает результат без дубликата.
6. Чтение тела, ожидание клиента и передача ответа не удерживают блокировку базы.
7. Отзыв прав действует на операции, прошедшие финальную проверку после отзыва. Уже подготовленный и разрешённый ответ может быть доставлен позже; полученный контекст отозвать невозможно.
8. Успешная выдача имеет устойчивую запись аудита; сбой аудита не приводит к отправке содержимого.

## 4. Безопасная миграция схемы 3

### 4.1. Проверка прежнего состояния

До изменения файла проверить snapshot старой записи по её версии схемы и версии алгоритма хэширования. Нельзя сначала менять schema_version, затем вычислять новый хэш и считать это подтверждением предыдущей проверки.

Для каждой записи определить один из результатов:

| Прежнее состояние | Результат |
| --- | --- |
| Draft или archived | Перенести статус без создания подтверждения. |
| Reviewed, старый снимок и источники совпадают | Сохранить проверку; вычислить эквивалентный снимок новой схемы. |
| Reviewed, изменены тело, ссылки или источник | Сохранить необходимость повторной проверки и конкретную причину. |
| Reviewed без известного формата снимка | `review_required`, без автоматического принятия. |
| Некорректный файл | Остановить миграцию до применения изменений, показать локальную диагностику. |

Метка access переносится в access_override консервативно. Изменение технического формата не снимает ограничение и не расширяет доступ. Историю проверки и прежний файл сохранять.

### 4.2. Прерывание и повтор

Применить журналируемую подготовку ко всем файлам миграции 3: записи, конфигурация, политика. Журнал содержит относительные пути, исходные и целевые хэши, версию и завершённые шаги. До замены проверить staged SHA-256; при продолжении проверить уже завершённые шаги.

Повторный запуск завершает только однозначную подготовленную операцию. При повреждении staged-файла или неожиданном изменении target остановиться, сохранив журнал и резервные копии. Миграция уже актуальной базы не переписывает снимки. Сервер не начинает обслуживание, пока состояние миграции неоднозначно.

## 5. Идемпотентное создание черновика

### 5.1. Идентичность и квитанция

Ключ уникален внутри client ID. Digest вычислять из нормализованного DTO: фиксированный порядок полей, однозначная кодировка UTF-8, явно определённый порядок цитат. Различия в пробелах JSON и порядке его полей не меняют digest. Текст утверждения и цитат не обрезать и не менять незаметно.

Первый запрос возвращает `201` с минимальной квитанцией: ID записи, `status: draft`, ID операции и ревизия политики на момент создания. Повтор той же операции возвращает тот же код и квитанцию; заголовок `Idempotency-Replayed: true` отличает replay. Это результат создания, а не текущая карточка: последующее принятие или архивирование записи не меняет квитанцию.

Повтор не вызывает GetRecord и не требует scope read. Наличие scope draft и текущий доступ ко всем исходным зависимостям проверяются заново. Отозванный клиент получает `401`; отсутствие scope — `403`; закрывшийся источник — `404 resource_unavailable`, без квитанции. Создание не даёт external права читать произвольные черновики.

Тот же ключ с иным digest возвращает `409 idempotency_conflict`. Отсутствующий ключ или превышение лимита 128 символов — `400 invalid_request`. Использовать ограниченный документированный набор ASCII-символов; не включать ключ в ошибки и обычный аудит.

### 5.2. Устойчивое состояние операции

Ввести IdempotencyStore с состояниями `reserved`, `record_saved`, `completed`, `failed_validation`. До записи знания устойчиво сохранить резервирование: client ID, digest, заранее выделенный record ID, ID операции и ссылки/хэши зависимостей. Секреты и полный текст запроса в журнал не включать. API создания знания должно принимать заранее выделенный ID и проверять отсутствие конфликтующей записи.

Порядок:

1. Валидировать запрос и разрешения, найти существующую операцию или устойчиво зарезервировать ID.
2. Создать draft и сохранить идентификатор операции в его метаданных. Успешное сохранение файла остаётся каноническим фактом независимо от индекса.
3. Записать минимальную квитанцию и фазу record_saved, обновить индекс или отметить его отставание.
4. Устойчиво записать аудит и completed; только затем отправить ответ.

После прерывания:

- reserved без файла: тот же запрос продолжает создание с тем же ID;
- файл существует и соответствует операции: завершить индексацию, аудит и квитанцию, не создавать новый;
- ID занят несовпадающей записью: остановиться с `409 operation_recovery_required`;
- аудит недоступен: `503`, файл и операция остаются; повтор продолжает ту же операцию;
- ответ потерян после completed: повтор возвращает квитанцию.

Параллельные одинаковые запросы сериализуются по операции; разные ключи не должны ждать чтения чужого HTTP-тела. Реализация MVP может сериализовать только короткую фазу записи всех draft. Межпроцессная блокировка обязательна, если state допускает использование несколькими процессами. Альтернатива MVP — явно запретить запуск второго сервера с тем же state и базой.

До появления политики очистки не удалять завершённые ключи автоматически: удаление снова допускает создание дубликата. Ограничить общий размер state; при заполнении отклонять новые операции с `503`, сохраняя replay существующих. В документации определить резервное копирование state вместе с базой.

## 6. Запросы, блокировки и отзыв доступа

### 6.1. Обработка HTTP

Последовательность: проверка метода/Origin/лимитов → аутентификация и scope → ограниченное чтение/разбор JSON → подготовка кандидатов → финальная согласованная проверка и операция → аудит → неизменяемый DTO → HTTP-ответ.

На этапе чтения ограничить тело 1 MiB, глубину JSON 32 и время чтения, например 10 секунд с конфигурацией владельца. Учитывать запросы без Content-Length. Неверный JSON и неизвестные поля не попадают в Core. Не удерживать блокировку базы при ожидании тела, очереди или клиента.

Внести отменяемую ограниченную по времени блокировку операции вместо синхронного ожидания в общем middleware. Пример начальных ограничений: до 5 секунд ожидания записи, до 8 активных запросов и ограниченная очередь. Параметры задаёт владелец, клиент их не переопределяет. Переполненная очередь возвращает `429`, ожидание занятой базы — `503 retry_required`. RequestAborted прекращает ожидание и чтение; уже зафиксированная draft-операция остаётся восстановимой.

### 6.2. Точка разрешения ответа

Финальная фаза проверяет актуального клиента, scopes, ревизию политики, канонические версии записи/источников и записывает аудит. После неё создаётся фиксированный DTO без ленивого чтения файлов во время сериализации. Ответ может начать передачу после освобождения блокировок; это зафиксированная точка авторизации операции.

Если отзыв произошёл до этой точки, данные не выдаются. Если после — уже разрешённый ответ может завершиться, а следующие операции отклоняются. Такая семантика проверяема и не обещает остановку уже переданных байтов.

Определить единый порядок вложенных блокировок: реестр клиента → база знаний → состояние операции/аудит. Все компоненты, которым нужны несколько блокировок, соблюдают этот порядок. Не захватывать базу, а затем ждать реестр. Не держать эти блокировки во время сетевого чтения или отправки. Подготовка кандидатов может выполняться вне критической секции, но все используемые версии повторно проверяются перед авторизацией.

## 7. Реестр клиентов

ClientRegistry использует отдельную межпроцессную блокировку для полного цикла load–modify–save. Create, revoke и финальная проверка клиента используют согласованный снимок реестра. Запись через временный файл в том же каталоге и атомарную замену; токены по-прежнему хранятся только как SHA-256.

Отзыв идемпотентен и не может быть потерян из-за конкурентного create. Неверный или повреждённый реестр запрещает обслуживание, а не создаёт пустой набор или клиент по умолчанию. Локальная команда показывает понятную ошибку; HTTP возвращает безопасный `503`.

Unix-права и ограничения Windows документировать и проверять отдельно. Токены и registry/state не включаются в переносимый архив знаний. Второй сервер с тем же state должен быть либо явно запрещён блокировкой процесса, либо полностью поддержан тестами конкурентной записи; для MVP выбрать запрет.

## 8. Контракт ошибок и аудит

| Ситуация | HTTP | Код |
| --- | --- | --- |
| Нет токена, неизвестный или отозванный токен | 401 | unauthorized |
| Валидный клиент без требуемого scope | 403 | forbidden |
| Недоступный или отсутствующий ресурс | 404 | resource_unavailable |
| Ошибка формы запроса/диапазона | 400 | invalid_request |
| Превышение размера тела | 413 | request_too_large |
| Превышение очереди/частоты | 429 | rate_limited |
| Ключ занят другим запросом | 409 | idempotency_conflict |
| Нужен повтор из-за изменившейся версии | 409 | retry_required |
| Неоднозначное восстановление операции | 409 | operation_recovery_required |
| Недоступны аудит, реестр или база | 503 | service_unavailable |

Все ошибки возвращают JSON и request ID. Ни один ответ не содержит локальных путей, stack trace, токенов, запросов к экстрактору, количества закрытых записей или их названий. Для закрытого ресурса проверять разрешение до формирования подробной диагностики: повреждённый закрытый источник не должен отличаться от отсутствующего по сообщению об ошибке. Время ответа само по себе не обещается как полностью защищённый канал.

Аудировать успешные операции и отказы в доступе, ошибку scope, replay и восстановление. Для неизвестного клиента не писать токен или его хэш: использовать anonymous и request ID. Записи запросов, title/body/quote и содержимое Idempotency-Key в аудит не включать. Защитить аудит от исчерпания диска, сохранив лимиты хранения и ограничение анонимного трафика. Сбой аудита блокирует успешную выдачу; уже сохранённый draft остаётся в восстанавливаемой операции.

## 9. Поиск и cursor

Результаты поиска формируются из канонических разрешённых записей, без индексных устаревших body/access. Ошибка одной закрытой записи не раскрывается клиенту. Не возвращать общее количество до фильтрации.

Cursor должен ссылаться на позицию в разрешённой выдаче, а не раскрывать номер просмотренного кандидата в полном архиве. Подпись гарантирует целостность, но Base64 не скрывает payload. Поэтому использовать случайный непрозрачный идентификатор серверной сессии либо шифрованный токен с проверкой целостности. Для MVP выбрать короткую серверную поисковую сессию с TTL 10 минут и лимитом числа сессий.

Сессию привязать к client ID, profile/scopes, digest запроса, ревизии политики и сроку действия. На каждой странице заново проверять доступ и актуальность. При изменении политики сессию завершать с `409 retry_required`; клиент начинает поиск сначала. Не создавать пустую следующую страницу только из-за наличия скрытых кандидатов. Подмена cursor, использование другим клиентом и неизвестный cursor дают безопасную ошибку без метаданных исходного запроса.

## 10. План HTTP-проверок

### 10.1. Стенд

Добавить HTTP integration suite с запуском приложения на случайном loopback-порту, временной базой, registry/state и реальным HttpClient. Выделить фабрику приложения/host для тестов без копирования логики маршрутов. Дополнительно проверить отдельным процессом фактический bind и запуск из CLI-инструкции.

Тестовый набор содержит разрешённый источник, local_only, unclassified, повреждённый закрытый источник, reviewed/draft/stale/archived записи и запись со смешанными источниками. Фикстуры используют узнаваемые маркеры; тесты проверяют отсутствие этих маркеров в полном JSON, заголовках, cursor и ошибках.

### 10.2. Матрица авторизации

Для search, record read, source text и draft проверить оба профиля и каждую комбинацию требуемого/отсутствующего scope, а также отсутствие токена, ошибочный и отозванный токен. Проверить невозможность задать profile, access, status=reviewed и executable через JSON.

Проверить новую метку источника после поиска, до чтения, во время подготовки ответа и между страницами. Для гонок использовать управляемые барьеры/точки остановки, а не случайные задержки. Отдельно проверить отзыв клиента в финальной фазе авторизации.

### 10.3. Создание и восстановление

Проверить external с одним scope draft: первый запрос, тот же replay, другой digest, другой клиент с тем же ключом и два параллельных запроса. Считать файлы знаний и проверять единый ID. Перезапускать сервер после каждого шага reserved–record_saved–completed, после аудита и до отправки ответа. Тестировать ошибку индекса и аудита, последующее восстановление без дубликата, запрет replay после закрытия источника.

### 10.4. Отказы и конкурентность

Проверить медленное тело без Content-Length, превышение размера, обрыв соединения и переполненную очередь. Пока один клиент медленно отправляет тело, другой должен иметь возможность читать, а CLI — менять классификацию. Завершение после таймаута не оставляет заблокированную базу.

Запустить create/revoke в разных процессах с барьерами перед сохранением; отзыв не теряется. Проверить отказ запуска второго сервера с тем же state.

Для миграции проверить проверенную неизменённую запись, вручную изменённое тело, изменённый источник, отсутствующий snapshot, повреждённый staged-файл, прерывание каждого шага и повторный запуск. Проверить сохранение резервных копий и причин stale.

## 11. Порядок работ и приёмка

1. Зафиксировать HTTP-контракты и добавить тесты, воспроизводящие текущие четыре P1-проблемы.
2. Исправить проверку старого snapshot и журнал миграции 3.
3. Реализовать устойчивый IdempotencyStore и создание с заранее выделенным ID.
4. Исправить границы блокировок, межпроцессный реестр, отмену и таймауты HTTP.
5. Довести аудит, одинаковые ошибки ресурсов и непрозрачную пагинацию.
6. Пройти HTTP suite, чистую Release-сборку и CI на Windows, Linux, macOS; обновить `docs/agent-gateway.md`.

Этап принят, если все инварианты раздела 3 подтверждены тестами, первый и повторный external draft имеют один ID, изменённая запись не становится reviewed после миграции, отзыв не теряется при конкурентной работе и медленный клиент не удерживает базу. В отчёте реализации указать проверенный commit, фактические команды и результаты, пройденные платформы, пропуски и оставшиеся ограничения.

После приёмки следующий отдельный шаг — MCP-адаптер поверх AgentKnowledgeService и пилот с одним агентом на небольшом наборе разрешённых данных.
